# Архитектура Trader

## 1. Текущая архитектура (as-is)

Сервис на текущем этапе является рабочим каркасом с частично реализованными подсистемами.

Главный runtime-поток:

1. `cmd/trader/main.go` загружает конфиг (`internal/config`)
2. Инициализирует логирование (`internal/logger`)
3. Создает manager (`internal/manager`)
4. Запускает manager и ждет `SIGINT/SIGTERM`
5. Выполняет graceful shutdown

Особенность: сервис работает в outbound-only модели и не поднимает локальный HTTP API.

## 2. Реально существующие компоненты

### 2.1 Базовые системные

- `internal/config`: YAML-конфиг и env overrides
- `internal/logger`: многопоточное логирование (`error/out_request/ws_in/ws_out/audit`) с ротацией
- `internal/manager/manager.go`: lifecycle-контроллер (`Start`, `Stop`, `Status`)
- `internal/state`: persistence флага состояния процесса

### 2.2 Домен и интеграция

- `internal/core/exchange/types.go`: базовые типы домена (биржи, рынки, задачи, orderbook)
- `internal/core/messaging/message.go`: унифицированные структуры сообщений
- `internal/core/ws/ws.go`: логический WS pool для подписки/отписки и корреляции `event_id <-> request_id`

Важно: текущий `ws.Pool` выполняет логическую обработку и логирование событий; он не является полноценным сетевым движком подключений к биржам.

### 2.3 Task-подсистема

- `internal/task/types.go`: модели входных задач для подписок
- `internal/task/subscription_manager.go`: считает diff между старым и новым набором задач, вызывает subscribe/unsubscribe

## 3. Границы текущей реализации

Следующие подсистемы пока не собраны в полностью рабочий production-контур:

- Реальные биржевые драйверы и коннекторы
- Полноценный orderbook/market-data pipeline
- Исполнение торговых стратегий в runtime
- Полный monitor-поток с записью исторических данных в ClickHouse
- Полная оркестрация всех подсистем через manager

## 4. Целевая архитектура (to-be)

Целевая модель остается прежней:

- CTS-Core задает задачи и получает телеметрию
- Trader держит подключения к биржам, поддерживает подписки и стратегии
- Monitor и Trader роли могут работать независимо или совместно

Но большая часть этих блоков на текущем этапе относится к roadmap, а не к полностью готовой реализации.

## 5. Состояние интеграционного контракта

Документированные правила интеграции с CTS-Core считаются целевыми требованиями. Часть инфраструктурных элементов уже заложена (outbound модель, telemetry-oriented логирование), но полный end-to-end контракт еще требует доработки runtime-цепочки.
